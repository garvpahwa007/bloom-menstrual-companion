# Bloom project structure

Bloom follows the BloodLink frontend pattern: each feature owns its page and related behavior, while reusable components, configuration and application state have shared folders. The app is an npm workspace with frontend and backend packages. The structural refactor is on the local branch `refactor/bloodlink-structure`; review that branch before merging it into main.

## Workspace

```text
saheli-menstrual-companion/
├── package.json                 # Workspace and root command wrappers
├── package-lock.json            # Shared npm workspace lockfile
├── vercel.json                  # Static hosting routes and headers
├── README.md
├── READ_ME_FIRST.txt
├── docs/                        # Plans, reviews and dated validation reports
├── backend/
│   ├── src/config/             # Environment and database connection
│   ├── src/middlewares/        # Origin checks and safe errors
│   ├── src/modules/auth/       # Account routes, controller, service, model, validation
│   ├── src/modules/diary/      # Encrypted backup routes, controller, service, validation
│   ├── src/app.js              # Testable Express factory
│   ├── src/server.js           # HTTP process lifecycle
│   ├── scripts/                # Persistent local MongoDB and disposable test runners
│   ├── tests/                  # Real HTTP + MongoDB integration and security checks
│   └── postman/                # Collection, local environment and instructions
└── frontend/
    ├── package.json             # Bloom React/Vite package
    ├── index.html
    ├── vite.config.js
    ├── .env.example
    ├── public/                  # Static artwork, manifest and host files
    ├── scripts/                 # PWA build plugin and UI-test preparation
    ├── tests/                   # Unit, UI, accessibility and hosting checks
    ├── src/
    │   ├── main.jsx
    │   ├── App.jsx
    │   ├── pages/
    │   ├── components/
    │   ├── config/
    │   ├── context/
    │   ├── services/
    │   ├── constants/
    │   ├── utilities/
    │   ├── hooks/
    │   ├── assets/css/
    │   ├── content/
    │   ├── data/
    │   └── i18n/
    └── dist/                    # Generated production output
```

Keep setup and checks at the project root:

```sh
npm ci
npm run dev
npm test
npm run build
npm start
```

Root scripts delegate to both workspaces. `npm run dev` starts Vite at port 5173; `npm run dev:backend` starts Express at port 3000; `npm run db:dev` starts persistent development MongoDB at port 27018. `npm start` serves the built frontend and API from Express; `npm run preview` starts a frontend-only static preview. See [BACKEND_SETUP.md](BACKEND_SETUP.md). The root `package-lock.json` records the workspace dependencies, so use `npm ci` from the root. `frontend/dist/` is generated by the build and is the Vercel output directory or Netlify publish directory when the hosting project is rooted here.

## Feature ownership

Each screen has a feature folder under `frontend/src/pages/`. A `.page.jsx` file renders that screen. A feature-specific `.component.jsx` file stays beside the page when it is only used there. A `.service.js` file holds related browser-side calculations or transformations.

| Folder | Responsibility |
| --- | --- |
| `pages/today/` | Today overview and quick entry points. |
| `pages/log/` | Dated diary entry and symptom controls. |
| `pages/calendar/` | Calendar navigation and selected-day records. |
| `pages/insights/` | Diary-derived charts and repeated timing observations. |
| `pages/cycle/` | Shared cycle calculations and formatting helpers. |
| `pages/guidance/` | Care cards and evidence-based rule evaluation. |
| `pages/visit/` | Visit screen, summary aggregation and PDF generation. |
| `pages/learn/` | Lesson catalogue, lesson detail and instructional diagrams. |
| `pages/ask/` | Local question screen and sourced answer matching. |
| `pages/reminders/` | Reminder settings, weekday control and scheduling calculations. |
| `pages/pregnancy/` | Confirmed pregnancy mode and sourced weekly content display. |
| `pages/privacy/` | Export, restore, encryption and deletion controls. |
| `pages/cloud/` | Optional account and browser-encrypted cloud-backup UI. |
| `pages/settings/` | Language, display, diary and PIN preferences. |
| `pages/layout/` | Shared application shell and feature route rendering. |

The earlier grouped `Tracking.jsx`, `CareAndLearn.jsx` and `Preferences.jsx` files have been split into these pages and shared components. New feature UI belongs with its feature rather than in another grouped screen file.

## Routing and state flow

`frontend/src/main.jsx` mounts the default `Routing` component from `config/routing.config.jsx`. That configuration owns `BrowserRouter` and renders `App`.

`App.jsx` is a small wrapper around `DiaryProvider` and `pages/layout/home-layout.page.jsx`. `context/diary.context.jsx` owns diary state, browser persistence and app actions. The home layout consumes that context to render the shell, feature routes and app dialogs. `config/navigation.config.js` supplies navigation items, and `config/app-routes.config.jsx` defines every feature route.

```text
main.jsx
  → config/routing.config.jsx (BrowserRouter)
    → App.jsx
      → DiaryProvider
        → pages/layout/home-layout.page.jsx
          → feature pages and shared app controls
```

The refactor changes code organization. The app keeps its existing routes, local-storage compatibility, bilingual content and feature behavior. The legacy storage key `saheli.v1` remains so existing diaries are still read.

| `config/navigation.config.js` | Sidebar and mobile navigation items. |
| `config/app-routes.config.jsx` | Feature route definitions and route props. |
| `config/routing.config.jsx` | Browser router setup. |
| `config/pwa.config.js` | Production PWA registration and cache lifecycle. |
| `context/diary.context.jsx` | Diary state, persistence and app-level actions. |

| `hooks/use-local-speech.js` | Available local speech voices and playback state. |

| `content/` | Sourced lessons, FAQ answers, pregnancy education and safety text. |
| `data/` | Synthetic demo data. |
| `i18n/` | English/Hindi dictionaries and translation helpers. |

The `.service.js` name does not imply an HTTP service. These modules execute in the browser, including the storage service. The `services/http.service.js` client is the exception: it calls the optional Express account and encrypted-backup API. Calculations, Ask and local storage remain browser-side. Cloud uploads are explicit and encrypted before leaving the browser. External health-source links open the cited service separately when selected.

## Static assets, tests and deployment

Source artwork, icons, the manifest and Netlify host files live in `frontend/public/`. Their browser URLs stay rooted at `/`, such as `/bloom-mark.png` and `/manifest.webmanifest`; the workspace folder does not become part of the public URL. The build writes these files and the bundled application to `frontend/dist/`. The production PWA build plugin remains in `frontend/scripts/pwa-plugin.js`.

Automated tests live in `frontend/tests/`, and UI-test preparation lives in `frontend/scripts/prepare-ui-tests.mjs`. Run `npm test` at the project root. Root `vercel.json` supplies frontend-only SPA routing and static-file headers; Netlify copies `frontend/public/_redirects` and `_headers` into the built output. Deploy `frontend/dist` from an HTTPS static host.

The dated reports in this folder retain their historical test results. See [REFACTOR_VALIDATION.md](REFACTOR_VALIDATION.md) for checks performed on this local structural refactor and [VALIDATION.md](VALIDATION.md) for the earlier build’s recorded evidence and remaining review limits. No deployment of the refactor is implied by those earlier production checks.
